## 四、核心问题诊断

### 问题 1：一条简单查询迭代了 4 轮（严重度：高）

**表现**：一个只需按经费类别分组统计 5 月支出总额的查询，Agent 走了 4 轮 ReAct 循环才拿到正确结果。

**根因分析**：
- **第 1 轮**：LLM 生成的代码**遗漏了 5 月日期筛选条件**，统计了全部数据 → 结果 0（实际代码有 bug）
- **第 2 轮**：Agent 自己判断需要加筛选，但使用了**不存在的列名** "实际支出金额"（实际是 "实际支出 (元)")
- **第 3 轮**：纠正了列名，但带括号和空格的列名 "实际支出 (元)" 在 pandas 代码中仍需转义处理 → 仍失败
- **第 4 轮**：改用日期字符串匹配 `'2026-05'` 策略 → 终于成功

**本质原因**：LLM 对 Excel 列名中的特殊字符（括号、空格）处理不当，且缺乏列名校验机制，每次都从头生成新的 pandas 代码，而非在上一轮基础上微调。

### 问题 2：每轮 LLM 代码生成耗时过重（严重度：高）

**表现**：4 轮 tools 节点的 LLM 代码生成长达 11~25s，合计 74.0s。

**数据**：inspect_file 已告知列名 "实际支出 (元)"，但 LLM 仍需生成完整的 `pd.read_excel` + `groupby` + `sum` 代码模板（被截断的代码显示每次都在重复 `if isinstance(DATA_PATH, str) ... elif isinstance(DATA_PATH, list) ...` 的样板代码）。

**根因**：prompt 要求 LLM 每次都生成完整的数据读取 + 处理代码，而非允许增量修正。tools 节点的 LLM prompt 可能过于冗长。

### 问题 3：execute_data_query 单次执行偏慢（严重度：中）

**表现**：单次查询 15.8s ~ 28.8s，对于一个 7 行数据的 Excel 明显过重。

**推测**：
- 可能是代码沙箱冷启动延迟（每次新启 Python 进程）
- pandas + Excel 解析开销
- 或者查询工具内部包含了额外的等待/重试逻辑

### 问题 4：supervisor 最后一步异常（严重度：低）

**表现**：`supervisor:1` 标记为 ERR!（1.1s），最终答案仍正确输出。

**可能原因**：data_agent 完成后 supervisor 尝试判断是否需再路由，但 data_agent 已给出有效答案，handoff 回到 supervisor 时产生了类似于 problem_record_3 中的 `ParentCommand` 异常。

## 五、优化建议

| 序号 | 建议 | 预期收益 |
|------|------|----------|
| 1 | **列名校验前置**：inspect_file 后在 agent 节点生成列名映射 `{"实际支出 (元)": "actual_cost"}`，传递给 tools 节点使用标准化列名 | 消除轮 2-3 的列名错误 |
| 2 | **增量代码生成**：允许 tools 节点复用上一轮代码，只修改关键行（如从 `groupby` 改为 `groupby`+日期筛选），而非每次从头生成 | 减少 LLM 生成时间 50%+ |
| 3 | **查询模板化**：为常见的 `groupby + filter + sum` 模式提供预置模板，LLM 只填充列名和筛选条件 | 代码生成降至 3-5s |
| 4 | **沙箱预热**：常驻 Python 进程或进程池，消除每次查询的冷启动延迟 | 单次查询降至 ~5s |
| 5 | **Agent prompt 优化**：在工具调用前提示 "列名含括号时请用 `df['列名']` 而非 `df.列名`" | 避免轮 3 的语法错误 |

**理想优化后预期**：1 轮查询（列名预校验 + 预置模板 + 沙箱预热）→ 总耗时降至 **15-20s**（降幅 85%+）。
